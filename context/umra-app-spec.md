# УМРА.РУ — приложение. Спека v0.1 (черновик)

**Дата:** 27.07.2026. **Рамка:** нативный iOS+Android клиент на **существующем бэкенде umra.ru** (приложение B). Спека-до-кода: сначала контракт и тесты, потом реализация. Без денежных/маркетинговых метрик — только продукт и инженерия.

---

## 1. Цель и не-цель

**Цель v1:** дать мусульманину одно приложение, где он (а) подбирает тур на Хадж/Умру, (б) ежедневно пользуется Кораном и временем намаза. Утилиты — движок ежедневного возврата; туры — то, ради чего бизнес.

**Не-цель v1 (явно, чтобы не расползлось):**
- Оплата тура внутри приложения — нет. Модель прежняя: клиент платит оператору напрямую, приложение отдаёт лид (deep-link в мессенджер), как сайт.
- Своя лента/соцфункции, чаты, UGC — нет.
- Замена сайта — нет. Сайт остаётся, приложение — второй клиент того же бэкенда.

## 2. Стек и ключевые решения

| Решение | Выбор | Почему |
|---|---|---|
| Фреймворк | **Открыто — подбирается под задачу в моменте**, не зашито | ИИ выбирает стек при старте. Критерии выбора (важны они, не имя фреймворка): максимум переиспользования TS-логики сайта (API-клиент, `quran/`, `prayer/`), оффлайн, локальные уведомления, secure storage, желательно OTA-обновления (хотфикс без полного стор-ревью). RN/Expo, Flutter, native — любой, что закрывает критерии |
| Бэкенд | **Существующий Express + Postgres** (Timeweb) | Нового бэкенда не строим. Новое — только end-user auth и скоуп по user_id (раздел 4) |
| Auth мобилки | **Bearer-JWT** (не кука) + **Apple / Google Sign-In** | Куки в нативе неудобны. Apple/Google убирают стоимость SMS. Apple Sign-In обязателен, если есть другой соц-вход |
| Утилиты | **Offline-first** | Текст Корана бандлится в сборку; время намаза считается на устройстве (adhan) с API как фолбэк. Возврат не должен зависеть от сети |
| Хранилище на устройстве | Локальная БД (данные/outbox/прогресс) + secure storage для токена (Keychain/Keystore) | Конкретные библиотеки — по выбранному стеку |

## 3. Модули (функциональная спека)

### 3.1 Туры (Хадж / Умра)
- Каталог: списки/фильтры (тип, город вылета)/сортировки (дата ↑↓, цена, длительность, близость к Каабе) — как на сайте (`OperatorTours`, `Catalog`).
- Страница оператора: профиль 6 операторов (`operatorProfiles`), туры сгруппированы по месяцам.
- Карточка тура: детали, правило питания (только Умма Тур — `meals.ts`), CTA.
- **CTA = лид, не оплата:** deep-link в WhatsApp/Telegram/звонок с предзаполненным текстом и `cid:` (паттерн `whatsappUtils`), номер — наш.
- Источник: `/api/tours`, `/api/operators`. Только чтение, публичные таблицы.

### 3.2 Коран
- Ридер: список сур, экран аята, перевод/транслитерация (как на сайте, `src/lib/quran`).
- Аудио: плеер, плейлисты, история прослушивания; стрим через `/api/quran-audio-proxy`, кэш прослушанного.
- **Закладки, прогресс чтения/прослушивания** — локально + синк (раздел 4). Таблицы `quran_bookmarks`, `quran_reading_progress`, `quran_user_settings`, `quran_listening_history`.
- Оффлайн: текст доступен без сети.

### 3.3 Время намаза
- Расписание по геолокации/городу, календарь на месяц, обратный отсчёт до следующего, выбор мазхаба (влияет на Аср).
- **Локальные уведомления намазов** — планируются на устройстве, работают оффлайн и без сервера (ключевая фича возврата; преимущество натива над web).
- Расчёт на устройстве (adhan) по координатам; `prayer_times_cache`/`/api/prayer-times-proxy` — фолбэк/сверка.
- Настройки уведомлений (какие намазы, за сколько минут) — синкаются.

### 3.4 Аккаунт и синхронизация
- Вход: Apple / Google (опц. телефон-OTP позже). Гость может пользоваться без входа — состояние локально; при входе локальное состояние мёржится в аккаунт.
- Синк прогресса/закладок/настроек между устройствами по `user_id` (раздел 4).
- Профиль, выход, удаление аккаунта (требование сторов + ФЗ-152).

## 4. Данные и синхронизация

**Принцип: один источник правды — Postgres за Express. «Синк» = клиенты пишут через одно API.**

**A. Контент** (туры, операторы, Коран, намаз): read-through тех же эндпоинтов + локальный кэш для оффлайна. Правка в админке → приложение видит при следующем pull.

**B. Состояние пользователя** (закладки, прогресс, настройки):
- **Write-through + оптимистичный локальный кэш:** изменение пишется локально сразу + upsert в API.
- **Оффлайн-outbox:** мутации в очередь, флаш при онлайне.
- **Разрешение конфликтов:** `updated_at`, last-write-wins по полю; прогресс чтения — max(позиция). Без CRDT.

**Новое на бэкенде (минимум, явный список):**
1. Таблица `app_users` (id, provider, provider_uid, created_at).
2. `/api/user/auth` — верификация токена Apple/Google → выпуск app-JWT (bearer).
3. Middleware `ensureAppUser` (bearer, роль `user`), рядом с `ensureAuth`/`ensureManager`.
4. Скоуп по `app_user_id` на `quran_*` и префы намаза: пользователь читает/пишет **только свои строки**. Расширение модели `AUTH_REQUIRED_READ_TABLES` (B.4) новым тиром «своё по user_id».
5. Миграция: как `quran_*` привязаны сейчас (анон device-id / никак) → добавить `app_user_id`, перелить device→user при первом входе.

---

## 5. Нефункциональные требования

- **Оффлайн:** Коран (текст) и намаз (расчёт+уведомления) полностью работают без сети. Туры — из кэша с пометкой «обновлено …».
- **Производительность:** холодный старт < 2 c до полезного экрана; списки туров/сур — виртуализация.
- **Безопасность / ФЗ-152:** согласие на обработку ПДн при входе (как на сайте — встроенные согласия); токен в SecureStore; чувствительные данные не кэшировать в открытом виде; удаление аккаунта чистит и локальное, и серверное.
- **Уведомления:** локальные (намаз) — на устройстве; серверные пуши (APNs/FCM) — вне v1.

## 6. Принудительные тесты — по радиусу поражения

**Полное покрытие (ломается дорого — данные/auth/синк):**
- Жизненный цикл токена: выпуск, рефреш, протухание, выход → нет доступа к чужим строкам.
- Скоуп по user_id: пользователь A не читает/не пишет строки пользователя B (тест на дыру, не на счастливый путь).
- Оффлайн-outbox: запись оффлайн → флаш при онлайне → ровно один upsert, без дублей и потерь.
- Конфликт-резолюшн: две правки одной записи → выигрывает max(updated_at); прогресс → max(позиция).
- Согласие ФЗ-152: без согласия аккаунт не создаётся; удаление аккаунта реально чистит обе стороны.
- Расчёт намаза: сверка adhan с известными таблицами по городам/мазхабам (цена ошибки = человек пропустил намаз).
- Лид-CTA: deep-link несёт корректный `cid:` и номер.

**Лёгкое покрытие (UI, ридер, навигация):** смоук-тесты, снапшоты ключевых экранов.

## 9. Последовательность (озёра, не океан)

| Веха | Что | Приёмка |
|---|---|---|
| **M1 — MVP, август** | Туры (чтение) + Намаз (расчёт+локальные уведомления) + Коран (ридер, оффлайн). **Без аккаунта**, состояние локально | Ставится, работает оффлайн, лид-CTA шлёт `cid` |
